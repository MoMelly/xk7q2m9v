## 1. 竞品与基线

### 1.1 酒馆（SillyTavern）——不是竞品，是功能基线

你嫌它麻烦，但麻烦的不是功能，是**装配**。它的能力拆开看：

| 酒馆的东西 | 本质 | 我们的处理 |
|---|---|---|
| 角色卡 V2（PNG 内嵌 JSON） | 人设包，字段 `description` / `personality` / `scenario` / `first_mes` / `mes_example` | **直接支持导入**。你手上已有的卡不用重做 |
| 预设 Preset | 主提示词 + 采样参数 + 输出模板 | 内置成"玩法包"，只暴露 3 个开关，不给你 40 个滑条 |
| 世界书 Lorebook | 关键词触发的设定条目，命中才注入 | 支持导入 + 关键词触发，界面叫"设定集" |
| 变量 + 状态栏 | 正则抓回复里的数值，渲染成面板 | 做进"角色状态"面板（好感度、地点、时间、情绪） |
| 正则 Regex | 清洗模型输出、替换显示 | 内置常用（去 markdown、去括号旁白）+ 可编辑 |
| 宏 `{{char}}` `{{user}}` | 变量插值 | 支持 |
| 群聊 | 多角色轮流发言 | 支持 |
| 扩展 / STscript | 任意脚本 | **不做**。这是它复杂度的来源 |
| 向量记忆 RAG | 语义检索历史 | 简化成本地关键词 + 摘要，够用 |

**结论：抄它的数据格式和玩法，不抄它的装配方式。** 它能导入的，我们能导入；它要装 Node 开代理填参数的，我们做成一个开关。

上表里「变量 + 状态栏」「可编辑正则」「宏插值」仍是规划，代码里没有；已落地的范围见 §6.2，补齐顺序见 ROADMAP.md 第 3 节。

### 1.2 中文「小手机」品类

| 产品 | 值得抄 | 不值得抄 |
|---|---|---|
| Shine 拾光 | Galgame 式演出（立绘+BGM 跟剧情）、角色发图发视频 | 邀请码注册、云端存记录、268MB |

## 2. 产品定义

一台只有你自己能进的假手机。点亮屏幕看到锁屏，解锁进桌面，图标里有聊天、相册、动态、备忘录。里面的角色按自己的作息生活，按你导入的卡和预设说话。

**核心抽象：玩法包（Playbook）**

酒馆麻烦在"每次都要重新配一套"。我们把它打包成一个可切换的单元：

```
Playbook = 主提示词 + 采样参数 + 正则组 + 变量表 + 界面皮肤 + 绑定的设定集
```

内置几套，一键切换：

| 玩法包 | 是什么 |
|---|---|
| 日常 | 普通微信式聊天，角色按作息回话 |
| 剧情 | 有场景推进，回复带旁白 |
| 直播体 | 角色在开播，界面变成直播间：在线人数、弹幕、礼物 |
| 群聊 | 多角色轮流发言，会互相接话 |
| 信箱 / 日记 | 单向书写体，异步感强 |

实现上收敛成 `RoleplayPreset` 的四个内置枚举（日常 / 剧情 / 直播 / 信件），用户不能新增或改写玩法包；理由见 §6.2。群聊不是玩法包，是 `Companion.isGroup` 上的开关。直播目前只有提示词，界面还是普通聊天页。

**明确不做**：账号登录、云同步、实时音频流、多人房间、上架 App Store、Android、任意脚本扩展。

## 3. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| UI | SwiftUI（iOS 26 起） | 液态玻璃只有原生有 |
| 工程文件 | **XcodeGen**（`project.yml`） | `.pbxproj` 是二进制式 XML，手改必炸、无法 diff。yml 描述工程，CI 生成 |
| 持久化 | **SwiftData** | 模型只有 4 个、关系简单，比手写 SQLite 少一半代码。代价是迁移过程不透明，所以加字段一律带默认值，改结构前先落 VersionedSchema（见 STANDARDS.md 第 3 节）|
| 网络 | URLSession + AsyncThrowingStream | 原生流式，零依赖 |
| 密钥 | Keychain（`whenUnlockedThisDeviceOnly`） | 不进 UserDefaults、不进代码、不进日志 |
| 离线 TTS | **Sherpa-ONNX + Kokoro** | 见 §4 |
| 语音识别 | iOS 原生 Speech（离线包） | 免费、无需联网 |
| 依赖 | SPM：sherpa-onnx | 依赖越少，五年后越能跑。SwiftData 是系统框架，不算依赖 |
| CI | GitHub Actions macOS runner | 你没有 Mac，云端代替 |

不引入：GRDB / Realm / FMDB 这类第三方持久化库、任何 UI 组件库、任何网络封装库。SwiftData 是系统框架，不算外部依赖；选它的理由见上表，落地结构见 §6.2。

## 4. 语音方案（实测数据）

| 方案 | 自然度 | 延迟 | 体积 | 判断 |
|---|---|---|---|---|
| AVSpeechSynthesizer（系统） | 低，机械感明显 | 几乎 0 | 0 | 只作兜底 |
| Piper / VITS（Sherpa-ONNX） | 中等 | ~120ms | 80-150MB | 做"快速模式" |
| **Kokoro-82M（Sherpa-ONNX）** | 好（TTS Arena 2026-01 Elo 1170，高于 OpenAI TTS 的 1158） | ~2.5s/句 | 量化后约 86MB | **主选** |
| 云端 TTS | 最好 | 200-500ms | 0 | 可选，要花钱 |

**怎么解决 Kokoro 的 2.5 秒**：分句流式。回复一到就按句切，第一句生成完立刻播，后面边播边生成。耳朵感知的是"停顿一下然后开口"，不是"等 2.5 秒"。

**必须说清的局限**：离线中文 TTS 的上限就是"清楚、不难听"，做不到真人的情绪起伏和气息。要那种效果只能走云端，按字收费。

**通话模式（模拟）**：不做实时音频流。点通话 → 全屏通话界面（头像/计时/挂断）→ 你说话走系统离线识别 → 文本模型生成 → TTS 念出来，中间插 0.5–1.5 秒随机停顿。观感接近真通话，延迟可控，成本为零。

## 5. 架构

```
Features (SwiftUI)      ← View + ViewModel
   ↓
Domain (纯 Swift)       ← Entities / UseCases / Protocols，禁止 import SwiftUI
   ↓
Data                    ← SwiftData 实现 / LLM 客户端 / TTS 引擎
   ↓
Support                 ← Keychain / Clock / Notifier / Log
```

CI 检查：`Domain` 里出现 `import SwiftUI` 或 `import SwiftData` 直接判失败（由 `scripts/check_standards.py` 执行）。跨层只走协议。

## 6. 数据模型

### 6.1 规划时的设计（v1，未落地）

最初打算拆成 10 个实体：CharacterCard / Character / Conversation / Message / Playbook / Lorebook / ChatState / Memory / Moment / Settings。

### 6.2 实际落地的设计（4 个实体，已实现）

| 实体 | 关键字段 |
|---|---|
| `Companion` | `uid`、`name`、`avatarTintRaw`、`persona`、`greeting`、`presetRaw`、`replyLengthRaw`、`isGroup`、`membersNote`、`wakeHour` / `sleepHour`、`memorySummary` / `memoryCursor`、`totalReplies`、`lastMessageAt`、`sortIndex`、`messages` |
| `StoredMessage` | `uid`、`characterUID`、`roleRaw`、`text`、`speaker`、`isNarration`、`createdAt`、`character` |
| `MomentPost` | `uid`、`characterUID`、`characterName`、`text`、`createdAt`、`tintSeed` |
| `WorldEntry` | `uid`、`characterUID`（空=全局）、`keywords`、`content`、`enabled`、`createdAt` |

**合并的理由**（逐条对应 v1 里的拆分）：

| v1 拆法 | 为什么合了 |
|---|---|
| CharacterCard 与 Character 两张表 | 我们不做"原始卡 + 覆盖字段"的双层模型。导入一次就把字段写进 `Companion`，用户改的就是最终值。多一层同步等于多一处不一致 |
| Conversation 单独一张表 | 一个角色一个会话，一对一。拆出去后每次查列表都要 join，而换来的能力（一个角色多个会话）现在的界面根本没入口 |
| Playbook（玩法包）一张表 | 玩法包从"可编辑的数据"降级成"枚举 + 提示词段落"，四个内置包写在 `RoleplayPreset` 里。用户改不了、也不需要改 |
| ChatState（变量表） | 还没做。等变量系统真做了再加表，现在建一张空表只是占位 |
| Memory 独立表 | 改成 `Companion` 上的两个字段：`memorySummary` 和 `memoryCursor`。当前只做滚动摘要，一条记录足够 |
| Settings | 不进数据库，走 UserDefaults + Keychain。设置项是标量，塞进 SwiftData 没有收益 |

`ChatMessage`（Domain 实体）与 `StoredMessage`（持久化模型）是两种东西：前者是送给模型的最小结构（role + text），后者还带说话人和旁白标记。转换点只有 `StoredMessage.asChatMessage` 一处。

跨会话的世界状态不是第五个 SwiftData 实体：`Domain/State/WorldState` 是一份 Codable JSON，由 `WorldStore.shared` 单独存取。人物级记忆、心声、当日日程、心情、当前曲目、使用记录都在这里，加字段不用迁移，备份直接拷文件。会话级摘要仍在 `Companion.memorySummary`，两者不重复。

### 6.3 提示词装配

`PromptBuilder.systemPrompt` 是唯一入口，顺序固定：

```
身份 → 人设 → 对话形式 → 群聊规则 → 长度 → 时间与作息 → 会话记忆摘要 → 世界状态（人物事实 / 未了结的心声 / 日程 / 心情 / 正在听 / 可查的手机记录）→ 设定集命中 → 输出约束 →（仅按次计费）状态块格式说明
```

每段独立可读，出问题时能一眼看出是哪一段注入坏了。`Features/` 层不允许自己拼提示词，`check_standards.py` 会扫特征字符串。

### 6.4 关于虚拟时钟

v1 写过"所有业务时间走 `VirtualClock.now()`"。**没有做**：它只有一个用途——把时间调到未来看角色反应，而真实使用里没人需要。现在统一用 `Date()`，格式化走 `TimeFormat`。

每期都是能装到手机上跑的产出。「代码」一列只说明写没写，不代表验没验证过——中间那一列的差别很关键。

| 期 | 目标 | 验收标准 | 代码 | 验证 |
|---|---|---|---|---|
| **P0** | 打通链路 | 手机上打开显示一句话，内容是你要的模型生成的。CI 能出 ipa | 完成 | **真机跑过** |

## 9. 工程纪律（防屎山）

1. 一个文件一个类型，文件名 = 类型名
2. 垂直切分目录，禁止垃圾桶目录
3. Domain 层禁止 import UI 与数据库框架，CI 强制
4. 对外依赖走协议，实现只在 `App/` 装配
5. 状态唯一来源（`@Observable` Store），View 不改数据
6. 数据库迁移显式编号，禁止删库重装
7. 每次改动附一行验收步骤，没验收不算完成
8. 架构决策写进本文对应章节（数据模型见 §6、语音选型见 §4、签名方案见 §10），不在别处另开一份容易过期的清单

## 10. 签名与续签（你最担心的部分）

### 免费签名到底有多麻烦

| 事项 | 频率 | 需要你动手吗 |
|---|---|---|
| 证书续签 | 每 7 天 | 配好 SideStore 快捷指令自动化后，理论上不用。**失败时要手动点一次 Refresh All** |
| 前置条件 | 一直 | 手机连 Wi-Fi、LocalDevVPN 常开（状态栏会有 VPN 图标） |
| 配对文件失效 | iOS 大版本更新后 | 需要连一次电脑重新生成 |
| 开发者模式 | 重启手机后 | 需要在设置里再确认一次 |
| App 数量 | — | 最多 3 个（含 SideStore 自己），够用 |

**实话说**：自动化能覆盖大部分情况，但它不是零维护。一年里你大概会遇到三五次"App 打不开，得打开 SideStore 点一下"。

### 摆在你面前的两条路

| | 免费自签 | 开发者账号 |
|---|---|---|
| 花钱 | 0 | 约 700 元/年 |
| 续签 | 7 天一次（自动化） | 一年一次 |
| App 上限 | 3 个 | 无 |
| 真推送 | 没有 | 有（我们不需要） |
| 出问题 | 你自己修 | 你自己修 |

**建议：先走免费，P2 之后再评估。** 你不用现在就决定——代码一行都不用改，只是签名方式换一下。等真正用两周，你就知道那点麻烦能不能忍。如果嫌烦，随时换。

### 关于 Apple ID：不需要新手机号

你手上本来就有两个号：系统里登录的主号（存照片、备份、iCloud 那个），和下载国外软件用的港区号。

**用港区号签名，别碰主号。** 理由不是港区号更安全，是风险不对等：主号出事要连带照片和备份，港区号出事只是少一个下载渠道。

SideStore 只在 App 内登录这个账号，不碰你系统里的 iCloud 和 App Store。就算苹果触发风控要求改密码，你的 App Store 也不会掉线，影响的只是 SideStore 自己。

**也不需要新手机号。** 免费签名从来不要求"专用的号"，一个号码通常能验证 2-3 个 Apple ID，超过才被拒。真有一天要换号，你现在这个号码就够用。

代价只有一个：换号重签等于重装，App 沙盒被清空，聊天记录会没。所以 §8 里把"导出"从 P7 提到了 P2 —— 自签 App 的数据随时可能因为重装消失，这不是保险，是常态。
